# Lyntai 3.0 Adoption Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Upgrade the four Lyntai packages from 2.5.0 to 3.0.0, set `ReinforceOn = Expansion` on the facts memory engine, and prove the whole app still works via the full e2e run.

**Architecture:** Pure dependency adoption — no new modules. Gatherlight implements none of Lyntai 3.0's broken seams (verified against `docs/migration-2.5-to-3.0.md` in the Lyntai repo), so the bump is expected to compile clean; the one deliberate change is a `GraphMemoryOptions` on the existing `UseGraph()` call. Lyntai's own FluentMigrator migration upgrades stored memory automatically at startup — no data work anywhere.

**Tech Stack:** .NET 10 / ASP.NET Core, Lyntai 3.0.0 from nuget.org, the repo's own devtools loop (`node devtools/dev.mjs build|e2e`).

**Spec:** `docs/superpowers/specs/2026-08-17-lyntai-3.0-adoption-design.md`

**Why no new unit tests (read before executing):** this plan changes no Gatherlight logic — it swaps a library version and sets one option whose behaviour lives entirely inside Lyntai (which tests it upstream, including a 2.5-row-under-3.0 compatibility fact). The acceptance gate is the existing e2e fleet: 48 suites that self-host the server with a stubbed claude CLI, of which `p48` drives the fact index (the one consumer of the changed engine) end to end. Writing a new Gatherlight test that re-asserts Lyntai's internals would test the dependency, not this app.

**Commit rule:** every commit below needs the owner's explicit go-ahead (repo rule; approval for this plan's execution counts if the owner grants it at kickoff).

**Known flake:** the e2e runner on Windows occasionally hits a libuv teardown abort AFTER a suite prints its PASS marker. Trust the printed per-suite PASS and the final `e2e: N/M passed` line; re-run before investigating any abort.

**Files:** none modified (unless a suite trips on intended 3.0 behaviour — see Step 2).

- [ ] **Step 1: Run the whole fleet**

Run: `node devtools/dev.mjs e2e all` (allow ~15+ minutes; suites self-host the server against isolated `devtools/_e2e-*` data folders with the stubbed CLI)

Expected: `e2e: 48/48 passed`. Remember the Windows teardown-abort flake from the header: a suite that printed PASS and then aborted counts as passed — re-run it alone (`node devtools/dev.mjs e2e p48`) before treating anything as a failure.

- [ ] **Step 2: If (and only if) a suite fails on intended 3.0 recall behaviour**

The changes 3.0 makes at runtime with no code change: recall is RRF-ranked, keyword matching is term-wise (wider candidate sets), CJK queries expand to trigrams, and a plain recall no longer reinforces. `p48` was pre-checked against these: its assertions (graph answered, `retrievability` in (0,1], co-recall linking, expansion reaching neighbours) are invariants 3.0 preserves — linking is NOT gated by `ReinforceOn`. So a p48 failure is more likely a real regression than an intended change. Only adjust an assertion when you can point at the specific migration-guide sentence that predicts the new value; otherwise treat it as a bug, use superpowers:systematic-debugging, and check the server log in the suite's `devtools/_e2e-*` data folder (`state/logs/`) first.

If an assertion is legitimately adjusted, commit it separately (with owner approval):

```bash
git add devtools/scripts/e2e/<suite>.mjs
git commit -m "test(e2e): align <suite> with Lyntai 3.0's documented recall behaviour"
```

- [ ] **Step 3: Nothing to commit when green**

A clean `e2e: 48/48 passed` ends this task with no diff.
