### Task 1: The Claude CLI update survives a transiently held file

**Why.** In p50 case H under fleet load, an update over a running CLI failed at 97% with "The process cannot
access the file because it is being used by another process." The 1.3.0 notes promise that updates no longer
fail while the CLI is in use. The exception came from `ReplaceBinary`'s fallback,
`File.Move(dest, aside)` (`ResourceProvisioner.cs:855`). It sits inside the `catch` with no retry, and a sharing
violation there escapes. The likely holders are antivirus scanning the exe, or the app's own `auth status`
probe: `ResourcesController.Provision` calls `_claude.Invalidate()`, and the next panel poll spawns `dest`.

There is a second hole. If line 855 succeeds and line 856 (`File.Move(staged, dest)`) then throws, there is no
`claude.exe` at all, while `version.txt` still names the old version.

**Files:**

- Test: `devtools/scripts/e2e/p50.mjs` (case H block ~372-436, port `PORT_PROVISION = 5509`, which is in the reserved band, so run it shifted)

```csharp
    /// <summary>Move the verified binary into place, tolerating a copy that is CURRENTLY RUNNING. Windows
    /// refuses to overwrite a loaded image, and an update is exactly when one may be mid-chat — so fall
    /// back to renaming the old file aside (which Windows does allow) and let the next sweep delete it.
    /// Failing the whole install because a turn was in flight would make updates unreliable by design.
    /// <para><b>A running image refuses the overwrite with ACCESS DENIED</b>, which .NET raises as
    /// <see cref="UnauthorizedAccessException"/> — NOT an <see cref="IOException"/>. This caught only the
    /// latter for months, so the fallback never ran in the one case it exists for and an update during a
    /// chat failed with "Access to the path is denied" (measured, and pinned by <c>e2e-p50</c> case H,
    /// which updates under a really running binary). A sharing violation is the IOException half.</para>
    /// <para><b>A HELD file is transient, and the rename aside used to give up on it at once.</b> A scanner
    /// reading a fresh exe, or our own <c>auth status</c> probe spawned from it on the panel's last poll, opens
    /// it without FILE_SHARE_DELETE — and the rename fails with a sharing violation for as long as that lasts.
    /// That failed an update under load (p50 case H, 2026-09-24) while the release notes promised updates no
    /// longer fail in use. So both moves retry a sharing violation for a few seconds, and if the new binary
    /// cannot be moved in, the old one is moved BACK: a version marker naming a binary that is not on disk is
    /// an install that cannot run. Proof: <c>e2e-p50</c> case H2.</para></summary>
    private static async Task ReplaceBinaryAsync(string staged, string dest)
    {
        // Sweep any earlier displaced copy first — this is the only thing that ever deletes them.
        foreach (var stale in Directory.EnumerateFiles(Path.GetDirectoryName(dest)!, "claude.exe.old-*"))
            try { File.Delete(stale); } catch { /* still running or locked; next time */ }

        try
        {
            File.Move(staged, dest, overwrite: true);
            return;
        }
        catch (Exception ex) when (ex is IOException or UnauthorizedAccessException) { /* fall back below */ }

        var aside = $"{dest}.old-{Guid.NewGuid():N}";
        await RetryWhileHeldAsync(() => File.Move(dest, aside));   // permitted even while the image is loaded
        try
        {
            await RetryWhileHeldAsync(() => File.Move(staged, dest));
        }
        catch
        {
            try { File.Move(aside, dest); } catch { /* nothing more to try; the error below says what failed */ }
            throw;
        }
    }

    /// <summary>ERROR_SHARING_VIOLATION (32) or ERROR_LOCK_VIOLATION (33): another process has the file open
    /// in a way that forbids this operation, which is transient by nature.</summary>
    internal static bool IsHeld(Exception ex) => ex is IOException io && (io.HResult & 0xFFFF) is 32 or 33;

    /// <summary>~7 s in all — long enough for a scan or a probe, short enough that the panel's progress row
    /// never looks hung.</summary>
    private static readonly int[] HeldRetryMs = [200, 400, 800, 1600, 2000, 2000];

    private static async Task RetryWhileHeldAsync(Action op)
    {
        for (var i = 0; ; i++)
        {
            try { op(); return; }
            catch (IOException ex) when (IsHeld(ex) && i < HeldRetryMs.Length)
            {
                await Task.Delay(HeldRetryMs[i]);
            }
        }
    }
```

**Why.** `MemoryService` exports and imports every `llm.model.*` key, and import writes each one straight into
`app_config` (`MemoryService.cs:138`). That includes `llm.model.memory`, the judge's annotation model, which

### Task 3: A bound local model whose file is gone falls back — and says so

**Why.** `LlamaCppSource.IsConfigured` asks whether the runtime is on disk and ANY GGUF of the layer's kind is
(`LlamaCppSource.cs:162-178`). It never asks for the BOUND model. So a household that deletes the bound chat
GGUF by hand, while a reranker or another chat model remains, stays "configured". The judge is then wired
against a model the router cannot serve, and every recall returns NoOpinion. The same holds for 语义: another
embedder's presence keeps a missing one bound. `MemorySources.ResolveJudgeModel`'s own doc (~192-193) already
assumes a fallback "when the model file is gone" that the code does not deliver.

**Constraint:** the bind endpoint calls `IsConfigured` BEFORE it saves the new model
(`MemoryRecallController.cs:~506`, save at ~532). So model-awareness must NOT go into `IsConfigured`, which would
test the previous binding's model. It goes into the resolvers, as a separate `HasModel`.

### Task 5: The restart policy also protects a chat judge's tags

**Why.** `LlamaRestartPolicy.WhyNotNow` refuses to restart our router while 语义 embeds through it, or while a
reindex runs, because a fact written during the restart would lose its vector for good. A llama.cpp CHAT judge
has the same exposure. It ANNOTATES every write through the router (client `memory-llamacpp`), and annotation

dev-conventions all say what is left is "判断's verification, which fails open". That is true only for a
reranker judge.

and refused before the policy is asked. dev-conventions states this gap. So verification is on the real binary,
recorded in the runtime doc, in the same way the 语义 guard was verified.

### Task 8 (OWNER DECISION 2 — only if approved): make kind-filtered recall measurable

**Why this is a design task first.** A kind-filtered recall asks the engine for 100 candidates, and verification
looks up to 4× deeper: up to 400 for the judge, where a kind-less recall sees at most 96. That is where latency
and judge-input cost would break. The bilingual fixture has 60 facts, so every recall there already sees every
fact, and a kind filter changes nothing measurable. dev-conventions measuring rule (1) applies: the instrument
cannot express the effect.
