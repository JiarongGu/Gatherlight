## Task 1: restore, compile, and D176 routes as ONE unit

Bump the four packages to 3.4.0. Raise Dapper to 2.1.89, Microsoft.Data.Sqlite to 10.0.12 and
SQLitePCLRaw.bundle_e_sqlite3 to 3.0.5 (NU1605). Fix `ScoringService` `ListThreadsAsync(…, ct: ct)`, and fix
`FactIndex` `Encode(result.Reference)` for now (Task 3 finishes it).

D176 cannot be staged: renaming the prefix without writing routes silently loses live model changes.
- The prefix becomes `llm.route.`, NEVER `llm.model.`: a bare `haiku` would read as a provider id.
- Only `scorer` and `memory` become routes; `chat`/`extract`/`validate` stay `llm.model.` (they feed `--model`).
- Every write is `provider:model`. An empty value DELETES the key, because a bare provider means the backend default,
  not the consumer default.
- The provider id is stated beside `AnnotationModel` in `JudgeWiring` or on the source: `claude-cli` or `llamacpp`.
- Writers to change: the binding endpoint (`MemoryRecallController` ~615), the cortex scorer row
  (`CortexConfigService` 85/119/127), the memory bundle (`MemoryService`), and the backup reconcile (`BackupService`
  242).
- A one-off startup migration moves stored `llm.model.scorer` and `llm.model.memory`. For `memory`, the provider is
  decided from the settings binding, or the key is dropped (it is recomputed at start).
- Port `JudgeScopedModelRoutingStore` to `GetRouteAsync` first. Delete it only once `p52` 4/4b pass on routes alone.
- Suites: `p52` 4/4b/5, `p14`, `p47`, and a NEW `p16` scorer-route case (no suite sets the scorer model today).
- Check the publish output for the ModelContextProtocol.Core 2.2.0 transitive graph.
