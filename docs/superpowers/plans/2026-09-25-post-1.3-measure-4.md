## Run 8 — the pace on a CPU

The reranker notes and `next.md` describe what `RerankPace` does on "只有 CPU 等较慢的机器" and add 「这些还没有在只有
CPU 的机器上实测过」. This machine can run llama.cpp with **no GPU offload** (`n-gpu-layers = 0` in the router's preset —
a real CPU run on real hardware, stated as "this machine's CPU", not "every CPU").

**Instrument.** Run 6's long fixture and seed (no tags, 判断 off). Arms on a CPU-only router (a second bench router, or a
per-arm preset override — the bench must record which): BGE and mMiniLMv2, each cut (`rr`, knob off) and chunked with
the pace (`rrk`); plus `formula`, and the GPU `rrk:` BGE as the reference. The pace's activity is the OBJECT here, so the
I6 void guard must be relaxed for designated CPU arms only — recorded per arm, never silently. Record per recall: windows
sent, whether it was cut by the 60 s deadline, the verdict, wall time.

**Report:** found@8/top-1 per position; the count and order of deadline cuts (first recall? how many?); windows per
recall over the run (does the pace converge, to what?); serial latency. **Decision rule:** if on the CPU the chunked+pace
arm is significantly WORSE than the cut arm on `all` found@8 for either reranker, the default on a machine the pace
measures as CPU-slow must change (owner decision, with the numbers); otherwise the household sentences replace "not
measured on a CPU-only machine" with what was measured here.

## Run 9 — long and short facts in one recall

Every reranker note says mixed recalls are unmeasured: a long fact is scored as its BEST window, so with more windows it
has more chances at a high score than a one-window short fact.

**Instrument.** A mixed fixture built deterministically from the existing two (no model): 30 facts kept short (original
text) and 30 turned into long notes (Run 6's construction, answer at `end` or `beyond`), balanced across languages and
across the 240 questions' targets; seed with 判断 off. Arms: `formula`, BGE / mMiniLMv2 / LAMAR each cut and chunked.

**Decision rule:** chunking "costs short facts" if, on questions whose target is SHORT, chunked found@8 is significantly
worse than cut (paired, p < 0.05) for any reranker — then the notes must say so with the number, and a length-aware
fix (e.g. a window-count penalty) becomes a measured follow-up; otherwise the notes' "mixed recalls unmeasured" becomes
the result. Report long-target questions too.

## Task X — a reranker's device is MEASURED, not guessed (owner decision after Run 8b)

Run 8b (recorded as unread) left one descriptive fact that changes the product. On this laptop the Arc iGPU is 3–5×
SLOWER than the CPU for both rerankers. BGE on it judged 1 recall of 240, and mMiniLMv2 fitted only by reading one
window per note, which is worse than no judge. `--list-devices` can't tell an integrated GPU from a discrete one, so the
device list cannot answer "run this where?".

**Owner decision:**
- At first warm-up, time one small rerank batch on the CPU and one on each GPU.
- Run the reranker on whichever device measured fastest.
- Recommend mMiniLMv2 when even the fastest device is too slow for BGE.
- Don't guess from device names.

**Design (deviations need a stated reason):**

1. **What is measured.**
   - For each INSTALLED reranker GGUF (`GgufCapability.Reranking`) that has no current measurement, time the CPU (`device = none`) and every device that `--list-devices` answered with.
   - Spawn the provisioned `llama-server` STANDALONE, not as the router, with that section's own window (`ctx-size`/`batch-size`/`ubatch-size` = `DeclaredWindow ?? RerankBatch`), on a free loopback port. The port must never be a fixed or known one.
   - Wait for health, send one warm `/v1/rerank`, then time one fixed call. Kill the tree.
   - Test ONE device at a time. Never run two in parallel (Run 9's VOID).
   - Every wait and call is capped. A device that times out or fails is excluded, with its reason recorded.
   - The fixed batch is deterministic bilingual text. Its size is counted in the PACE'S unit (ms per pair token, `RerankPace`'s own token weights), so the measurement and the pace speak one unit through one counting.
   - A result is valid only if every document came back scored.
2. **Key and storage.**
   - Key the measurement by:
     - the model file (id plus size and mtime, or a hash);
     - the llama.cpp build tag;
     - the device list's ids and names. Strip the volatile "MiB free" figures, or every boot re-measures.
   - Persist it as derived state under the provisioned models dir. It must NOT travel in a backup: a device choice belongs to one machine, and `state/` isn't in the backup.
   - Re-measure only when the key changes.
3. **When.**
   - At every router start or restart WE perform (`EnsureServingAsync` / the restart path), before `WritePresets`, for rerankers lacking a current measurement.
   - That is once per model per key, behind the migration overlay (`LlamaWarmStep` is non-essential) or inside a bind's restart.
   - Never for an ADOPTED router: its presets aren't ours.
   - It runs under the one start/restart/stop lock.
   - `Dispose` must kill a measurement child. An orphaned llama-server is the failure this runtime already fought.
4. **Presets.** A measured reranker section gets `device = <fastest>`: a device id, or `none` for the CPU. With no valid measurement, write no device key (today's behaviour). Verify on the real binary:
   - that the router passes `device` to the child for a GPU id, not only for `none` (Run 8 proved `none`; Run 8b used an env var);
   - whether `n-gpu-layers = 99` beside `device = none` is harmless. The launch-contract comment and `p51` must say what is true for a CPU section.
5. **The pace.** When the bound reranker has a measurement for its chosen device, seed `RerankPace` with it instead of `SeedMsPerToken`. Otherwise the first recall on a slow device is cut at the deadline, as Run 8's was.
6. **The recommendation.**
   - Make "too slow for BGE" the SAME admission the runtime makes: a fresh pace seeded with BGE's best measured rate either would or would not send a one-window call for a reference page of candidates. Find and cite the candidate count the verifier actually sees; don't invent one.
   - Precedence: recent skips → BGE measured too slow → device probe says no GPU → BGE.
   - A measurement exists only after a download, so on an iGPU-only machine the badge can still offer BGE first and move to mMiniLMv2 once BGE is measured. State that limitation in the reason and the notes; don't hide it.
7. **Visible.** Where the household sees a reranker's row, say which device it runs on and that the choice was measured on this machine, with the measured figures in a unit a household reads. Every sentence must be true of the code (the reviewer checks). Embedders and chat models are unchanged; say so where it matters, and that whether they'd benefit is unmeasured.

**Tests.**
- e2e covers the choice, the preset key, the invalidation on a key change, the pace seed, and the recommendation flip.
- If the spawn half can be driven (for example, a fake llama-server reached through a measurement-only test seam), drive it. Otherwise state it as a real-binary-only gap.
- Confirm each new assertion FAILS with its half removed.

**Real binary, by hand, on this laptop** (`devtools/_rr-res` resources, never `local/state/resources`; never PID 19080):
- (a) Both GPUs visible: record per-device ms per 1,000 pair tokens for BGE and mMiniLMv2, the choice, and a real rerank through the router on it.
- (b) iGPU-only, emulated by `GGML_VK_VISIBLE_DEVICES` hiding the RTX: the choice (expected: the CPU for both), the preset, the recommendation, and a real rerank.
