# Lyntai 1.0 upgrade + migration fresh-start — design

Date: 2026-07-28

## Goal

Move Gatherlight onto **Lyntai 1.0.0** and collapse its own accreted FluentMigrator ledger (11
migrations) into a single clean **1.0 baseline**. A destructive DB reset is acceptable because the
whole-install export/import preserves all *durable* data.

## Why a fresh start is safe

Lyntai 1.0's one breaking change that reaches Gatherlight is a **migration baseline reset**: its 0.x
SQLite migrations were squashed into fresh `202607280001..0009` baselines. A pre-1.0 `gatherlight.db`
already holds `lyntai_*` tables created under the old migration numbers, so `UseSqliteStorage`'s 1.0
baselines would try to re-create existing tables → crash. The NET schema is unchanged (Lyntai proved
byte-equivalence); only the ledger renumbers. The public-surface shrink (`McpTool`/`ProviderDetect`/
`LyntaiChatClient` → internal, `AntiPrompts`→`StopSequences`, `Flavor`→enum, `IVectorStore.DeleteAsync`)
touches **nothing** in Gatherlight.

The whole-install backup (`BackupService`) preserves the durable data — markdown records
(`plans`/`household`/`.claude`/`uploads`), the data-repo git history, `state/settings.json`, and the
DB memory bundle (Library/Knowledge/Entities/Cortex). Chat history, scores, jobs, and mcp_servers are
intentionally *not* backed up (rebuildable/transient). So wiping the whole DB loses nothing durable.

We are the only user, so no in-place upgrade path / guard is built — the DB is reset outright.

## Changes

1. **Lyntai bump** — `Gatherlight.Server.csproj`: `Lyntai.Core` / `Lyntai.Providers.ClaudeCli` /
   `Lyntai.Storage.Sqlite` `0.31.1 → 1.0.0` (on nuget.org). Expect a clean compile; prove by building.
2. **App version** — `src/Directory.Build.props` `VersionPrefix 1.0.8 → 1.0.0` (re-stamp to mark the
   Lyntai-1.0 milestone; single user, so auto-update ordering is a non-issue).
3. **Migration squash** — delete all 11 files in `Modules/Fluent/Migrations/`, replace with one
   `202607280001_Baseline.cs` that builds the current **net** app schema directly. The two obsolete
   0.x→Lyntai data bridges (`202607190001`, `202607200001`) and the tables they retired
   (`chat_score`, `chat_session`, `chat_event`) are simply absent. FTS5 virtual tables + sync triggers
   stay raw `Execute.Sql`; ordinary tables use the fluent API. With the bridges gone, the app's
   migrations no longer depend on `lyntai_*` existing first (Lyntai's eager `UseSqliteStorage` stays).

### Net app-owned schema the baseline must reproduce

Tables: `app_config`, `chat_turn`, `plan_index`, `plan_asset`, `tool_cache`, `upload`, `data_commit`,
`zhiku_state`, `entity`, `knowledge`, `process_log`, `library_item` (+ unique index
`ux_library_item_kind_key`), `chat_feedback`, `job` (+ `ix_job_due`), `job_run` (+ `ix_job_run_job`),
`notification` (+ `ix_notification_unread`), `mcp_server` (with the 3 login columns appended last).
Virtual tables + triggers: `library_fts` (+ `library_item_ai/ad/au`), `knowledge_fts`
(+ `knowledge_ai/ad/au`).

## Verification

- **Schema-equivalence gate**: dump app schema from a fresh db built by the *old* migrations (golden,
  captured before any edit) vs. the new baseline; diff and reconcile any non-cosmetic difference
  (`devtools/_schema-dump.mjs`).
- **e2e**: `node devtools/dev.mjs e2e all` green — the suites exercise every repository, so a wrong
  column/type/index/trigger/FTS fails directly. This is the authoritative functional gate.
- Clean build; app boots.

## Reset the live `local/` (approved)

Destructive to the live DB, done with a safety net: (1) copy the current `local/` (at least its db)
to scratch + confirm the backup zip reads; (2) delete `local/state/gatherlight.db`; (3) start the
server (Lyntai 1.0 + the new baseline recreate the db fresh); (4) `POST` the backup zip to
`/api/backup/import`; (5) verify `/api/health` green + memory counts match the backup manifest.

## Risks

- Squash schema drift → schema-equivalence gate + full e2e.
- `local/` reset losing something outside the backup (chat/scores/jobs) — transient by design; the
  pre-wipe safety copy is the fallback.
