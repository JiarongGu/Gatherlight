# Lyntai 3.0 adoption — design

**Date:** 2026-08-17 · **Status:** approved
**Scope ruling (owner):** bump + accept the new defaults + `ReinforceOn = Expansion`; the
model-in-the-loop features stay off (declined-for-now list at the end).

## What and why

The sibling Lyntai library released 3.0.0 (on nuget.org) — the long-term-memory retention model
(FSRS/DSR forgetting curve, RRF ranking, review log, CJK-capable keyword recall) plus a pre-freeze
whole-library review. Gatherlight consumes `Lyntai.Core`, `Lyntai.Providers.Default`,
`Lyntai.Storage.Sqlite` and `Lyntai.Tools.Mcp.Hosting` at 2.5.0. This adoption upgrades all four
and makes exactly one deliberate configuration change.

Mapped against Lyntai's `docs/migration-2.5-to-3.0.md` (in the Lyntai repo), Gatherlight's breakage
surface is effectively zero:

- **No BYO seams.** We implement no age/retrievability/salience/retention policy, no custom
  `IMemoryGraphStore`, no `IJobStore` (our `job` tables are our own subsystem, not Lyntai jobs),
  no `ICliProviderDialect`, no `IGenerationRouter` (we don't reference `Lyntai.Generation`).
- **No tuned options.** The one engine registration is a bare
  `AddMemoryEngine("facts", e => e.UseGraph())` — none of the moved/validated knobs
  (`HopAttenuation`, `RelativeFloor`, `Decay`) were ever set.
- **No positional deconstructions** of the six records that grew trailing members. `FactIndex`
  reads `recall.Items` by property; `MemoryQuery`/`MemoryWrite` are constructed with named
  arguments; the renamed 2.5 seams (`IMemoryClock`, `IRetrievabilityPolicy`,
  `MemoryRetentionPolicy`) appear nowhere in this repo.
- **No `MemoryGrade.Authoritative`** — the fact index is deliberately the associative tier, so
  the authoritative-slots change cannot affect us.

So the expected shape is: version bump compiles clean; any surprise from the 3.0 naming sweep is
named by the compiler and fixed mechanically per the guide.

## Changes

### 1. Package bump

`src/server/Gatherlight.Platform/Gatherlight.Platform.csproj`: the four `PackageReference`s go
`2.5.0` → `3.0.0`. Surrounding comments stay accurate (none states a version).

### 2. `ReinforceOn` — Expansion-only was tried and REVERTED (a finding, not an omission)

The original design set `ReinforceOn = MemoryReinforcementActs.Expansion` on the facts engine,
on Lyntai D58's measurement (reinforcing only expansions beat the default on miss and pollution).
**e2e-p48 falsified it for this product:** co-activation linking rides the same gated
reinforcement step (`GraphMemoryEngine.ReinforceAsync` opens with the `ReinforceOn` check and
ends with the pairwise `LinkAsync`), and an expansion reinforces a single node — zero pairs. So
Expansion-only does not merely change reinforcement, it silences the model-free
facts-recalled-together linking that `expand_fact`'s reach-what-the-query-never-matched behaviour
is built on. p48 showed it directly: linked degrees all `0`, `expand_fact` reaching nothing.

The registration stays `UseGraph()` — the shipped default (`ReinforceOn = All`). The entrenchment
D58 guards against is already mostly gone in 3.0: `DsrOptions.ReinforceGain` ships at `0`, so a
recall refreshes an entry's age but no longer permanently lengthens its half-life. The reversal
and its reason are recorded in the comment above the engine registration so Expansion-only is not
re-proposed as an optimisation.

### 3. Defaults accepted as shipped

Nothing else is configured. What arrives by default, recorded here so the behaviour change is on
the record:

- **DSR (FSRS power-law) forgetting curve** — the 2.5 exponential curve is deleted upstream;
  stored stability rows keep their meaning by contract (no data migration).
- **`ReinforceGain = 0`** — a recall refreshes an entry's age but no longer permanently lengthens
  its half-life; durability now comes from salience and connectedness, not from the ranker's own
  choices being fed back.
- **RRF ranking default** (replacing the multiplicative policy).
- **Term-wise keyword recall + CJK trigram expansion** — a spaceless Chinese query now matches by
  character trigrams instead of exact-substring-or-nothing. Directly relevant to this household's
  data; no setup.
- **Review log on** (bounded, 10k rows/engine) — the raw material a future parameter-fitting pass
  needs; nothing in recall/ranking/pruning reads it back.

### 4. Data: automatic, one migration

3.0 delivers its whole schema change as one FluentMigrator migration, applied eagerly by
`UseSqliteStorage` during DI — the live data folder's `state/gatherlight.db` and every e2e data
folder migrate in place on first start. Backup/restore is unaffected: `knowledge` remains the
record of truth and import's `RebuildAsync` path is unchanged.

## Error handling

- A compile break from the naming sweep: fix mechanically; the guide names the mapping.
- An e2e failure from the *intended* recall changes (wider term-wise candidate sets, RRF order):
  adjust the assertion only where the new behaviour is genuinely correct — never to absorb a
  regression. What actually happened: p6's confidence-ordering assertion tripped on the RRF
  default (the guide-predicted class — adjusted to assert confidence is *carried*, since ordering
  belongs to the graph path now), and p48 tripped on the Expansion-only setting itself (§2's
  reversal — the pre-check claim that "linking is not gated by `ReinforceOn`" was wrong: the
  pairwise link lives inside the gated reinforcement method).

## Testing

`node devtools/dev.mjs build`, then the full `node devtools/dev.mjs e2e all` — p48 (fact index),
p36 (judge tools), p44 (agent MCP wiring) and p21 (egress audit) watch the Lyntai-adjacent seams.
Recall-behaviour changes are runtime, not compile-time, so e2e green is the acceptance gate, not
the clean build.

## Addendum (2026-08-17, later the same day): the model-backed steps are adopted after all

Owner ruling on review of the base adoption: *"you probably can adopt the latest features too."*
The two model-in-the-loop features move from declined to adopted, with the engineering that makes
their cost acceptable stated here rather than discovered later.

- **`AddMemoryVerification()`** — a model judges which recalled candidates actually answered the
  query. Adopted because the number is too large to leave: on Lyntai's measured corpus the
  model-free ranking is the miss rate end to end (100% of missed answers were in the candidate
  set, ranked below the cut), and a Claude-Haiku-via-CLI judge takes miss from 0.5357 to 0.1857 —
  more than every ranking-policy choice combined. Cost: ~3 s and one haiku call in the latency
  path of each `recall_facts`. Contained by routing: the verification request carries Lyntai's
  `Consumer = "memory"` tag with `Model` null, so `DefaultModelByConsumer["memory"] = "haiku"`
  plus the existing `AddLiveModelRouting` gives the judge a cheap default with a live
  `llm.model.memory` override — exactly the scorer pattern. `VerificationFilters` stays `false`
  (a verdict reorders, never drops), and the policy is fail-open *asymmetrically* (any failure is
  "no opinion", never "nothing relevant"), which is what keeps the stubbed-CLI e2e valid: the stub
  judge's nonsense leaves every ranking untouched.
- **`AddMemoryAnnotation()`** — a model labels each fact write with what it is ABOUT, so entries
  about the same entity link even when their text never names it. Cost: one haiku call per
  `remember_fact` (rare, agent-initiated). **The known trade, accepted deliberately:** the fact
  index's `RebuildAsync` re-writes every fact, so a backup import now annotates the whole corpus —
  roughly 2–3 s per fact of added import time. Accepted because import is rare, user-initiated
  disaster recovery, and the policy is fail-open: an unavailable CLI slows nothing and stores the
  fact without annotation; it can never fail the import.
- **`MemoryRecall.Answered` surfacing** — now has a consumer. `IFactIndex.RankAsync` returns
  `FactRanking(Hits, Answered)` and `recall_facts` adds an `answered` field when a judge actually
  ran (`true`/`false`; absent when nothing judged — e2e, or a failed judge). "A judge looked and
  found none" and "nothing was judged" call for different next moves from the agent, the same
  reason `ranked: graph|fts` exists.
- **Named LLM clients** — still not adopted: consumer-tag routing covers the sizing need without
  a second client to configure.
