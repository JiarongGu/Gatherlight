# Lyntai 3.0 adoption — design

**Date:** 2026-08-17 · **Status:** approved
**Scope ruling (owner):** bump + accept the new defaults + `ReinforceOn = Expansion`; the
model-in-the-loop features stay off (declined-for-now list at the end).

## What and why

The sibling Lyntai library released 3.0.0 (on nuget.org) — the long-term-memory retention model
(FSRS/DSR forgetting curve, RRF ranking, review log, CJK-capable keyword recall) plus a pre-freeze
whole-library review. Gatherlight consumes `Lyntai.Core`, `Lyntai.Providers.Default`,
`Lyntai.Storage.Sqlite` and `Lyntai.Tools.Mcp.Hosting` at 2.5.0. This adoption upgrades all four
and makes exactly one deliberate configuration change.

Mapped against Lyntai's `docs/migration-2.5-to-3.0.md` (in the Lyntai repo), Gatherlight's breakage
surface is effectively zero:

- **No BYO seams.** We implement no age/retrievability/salience/retention policy, no custom
  `IMemoryGraphStore`, no `IJobStore` (our `job` tables are our own subsystem, not Lyntai jobs),
  no `ICliProviderDialect`, no `IGenerationRouter` (we don't reference `Lyntai.Generation`).
- **No tuned options.** The one engine registration is a bare
  `AddMemoryEngine("facts", e => e.UseGraph())` — none of the moved/validated knobs
  (`HopAttenuation`, `RelativeFloor`, `Decay`) were ever set.
- **No positional deconstructions** of the six records that grew trailing members. `FactIndex`
  reads `recall.Items` by property; `MemoryQuery`/`MemoryWrite` are constructed with named
  arguments; the renamed 2.5 seams (`IMemoryClock`, `IRetrievabilityPolicy`,
  `MemoryRetentionPolicy`) appear nowhere in this repo.
- **No `MemoryGrade.Authoritative`** — the fact index is deliberately the associative tier, so
  the authoritative-slots change cannot affect us.

So the expected shape is: version bump compiles clean; any surprise from the 3.0 naming sweep is
named by the compiler and fixed mechanically per the guide.

## Changes

### 1. Package bump

`src/server/Gatherlight.Platform/Gatherlight.Platform.csproj`: the four `PackageReference`s go
`2.5.0` → `3.0.0`. Surrounding comments stay accurate (none states a version).

### 2. `ReinforceOn = Expansion` on the facts engine

`GatherlightApp.cs`:

```csharp
.AddMemoryEngine("facts", e => e.UseGraph(new GraphMemoryOptions
{
    ReinforceOn = MemoryReinforcementActs.Expansion,
}))
```

Rationale: `expand_fact` is a caller choosing to pay for full content — the closest thing the
engine observes to a *verified* retrieval — while a plain recall reinforces whatever the ranker
returned, mistakes included. Reinforcing only expansions beat the default on both miss and
pollution in every measured cell (Lyntai D58); Lyntai keeps the default at `All` only because an
application that never expands would then reinforce nothing, and we do expand.

The narrative comments that currently promise "recall reinforces what it returned" — the block
above the engine registration in `GatherlightApp.cs` and the `FactIndex` class doc — are updated
to say expansion is what reinforces. A comment describing retired behaviour is drift.

### 3. Defaults accepted as shipped

Nothing else is configured. What arrives by default, recorded here so the behaviour change is on
the record:

- **DSR (FSRS power-law) forgetting curve** — the 2.5 exponential curve is deleted upstream;
  stored stability rows keep their meaning by contract (no data migration).
- **`ReinforceGain = 0`** — a recall refreshes an entry's age but no longer permanently lengthens
  its half-life; durability now comes from salience and connectedness, not from the ranker's own
  choices being fed back.
- **RRF ranking default** (replacing the multiplicative policy).
- **Term-wise keyword recall + CJK trigram expansion** — a spaceless Chinese query now matches by
  character trigrams instead of exact-substring-or-nothing. Directly relevant to this household's
  data; no setup.
- **Review log on** (bounded, 10k rows/engine) — the raw material a future parameter-fitting pass
  needs; nothing in recall/ranking/pruning reads it back.

### 4. Data: automatic, one migration

3.0 delivers its whole schema change as one FluentMigrator migration, applied eagerly by
`UseSqliteStorage` during DI — the live data folder's `state/gatherlight.db` and every e2e data
folder migrate in place on first start. Backup/restore is unaffected: `knowledge` remains the
record of truth and import's `RebuildAsync` path is unchanged.

## Error handling

- A compile break from the naming sweep: fix mechanically; the guide names the mapping.
- An e2e failure from the *intended* recall changes (wider term-wise candidate sets, RRF order):
  adjust the assertion only where the new behaviour is genuinely correct — never to absorb a
  regression. p48's assertions (graph answers, retrievability ∈ (0,1], co-recall linking,
  expansion reaching neighbours) are invariants 3.0 preserves; linking is not gated by
  `ReinforceOn`.

## Testing

`node devtools/dev.mjs build`, then the full `node devtools/dev.mjs e2e all` — p48 (fact index),
p36 (judge tools), p44 (agent MCP wiring) and p21 (egress audit) watch the Lyntai-adjacent seams.
Recall-behaviour changes are runtime, not compile-time, so e2e green is the acceptance gate, not
the clean build.

## Records

After landing: a structural line in `docs/release-notes/next.md`. Commits only with explicit
owner approval, per repo rules.

## Declined for now (recorded so they are not re-proposed as oversights)

- **`AddMemoryAnnotation`** — subject labelling would improve linking, but costs one claude CLI
  spawn per fact write. Revisit if linking quality disappoints.
- **`AddMemoryVerification`** — the largest recall-quality gain in 3.0, but one claude CLI spawn
  in the latency path of every `recall_facts` call, against "token spend is reserved for actual
  planning". Revisit with the eval playground if recall quality becomes the bottleneck.
- **Named LLM clients / `MemoryRecall.Answered` surfacing** — no consumer for either yet.
