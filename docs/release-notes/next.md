### 更新 Claude CLI 时,文件被暂时占用也能装上

应用自己安装的 Claude CLI 在「资源 · Resources」里更新时,新文件要放到旧文件的位置上。如果这时恰好有别的程序
在读这个文件(比如杀毒软件在扫描刚下载好的程序),以前更新会直接失败,只显示「下载失败:The process cannot
access the file because it is being used by another process.」—— 而 1.3.0 的说明里写的是,更新 Claude CLI 时
不会再因为「正在使用」而失败。现在遇到这种情况,应用会等几秒再试;一直被占着的话,这次更新不装,并用中文说明
原因:

- 已安装的版本还在原处时:说明这次没能替换,**已安装的版本不受影响**,稍后再点「更新」。
- 如果旧版本已经挪开、却没能放回:如实说明现在暂时用不了,稍后再点「更新」或**重启应用**,都会先把旧版本放回去 ——
  哪怕那次下载本身失败了,也会先放回。
- 第一次安装、还没有旧版本时:只说这次没能装上,稍后再试,不会说「旧版本」怎样。

### 导出/导入「记忆」时,不再带上「判断」的模型

「判断」用哪个模型,是和它用哪个后端(Claude CLI 或本机模型)一起保存在设置里的;而导出的「记忆」文件不带
这份设置。以前导出文件仍会带上「判断」的模型名,导入到另一台安装时,那边可能拿一个本机模型的名字去问 Claude ——
Claude 不认识它,主题标注和检索时的判断就悄悄地都没有了。现在「记忆」文件只带「校准 · Cortex」里能设置的模型;
旧版本导出的文件即使带着这一项,导入时也会跳过。

**从整机备份恢复时**,备份里有这份设置,会整份恢复;应用同时会清掉当前安装里残留的「判断」模型记录,重启后以
恢复的设置为准。

### 本机模型的文件不见了,「判断」和「语义」会退回并提示

如果「判断」或「语义」绑定的本机模型文件被删掉了,而模型目录里还有别的同类模型,以前应用仍当作这一层已经配好:
「判断」每次检索都悄悄地没有意见,「语义」绑着一个不存在的模型。现在启动时会发现这一点:

- 「判断」退回 Claude CLI。启动提示会写明是哪个模型不在了、退回后**要消耗账号额度、事实内容会发给 Claude**;
  如果 Claude CLI 还没登录或没有安装,也会说明这时既不标注也不核对,以及怎么处理。
- 「语义」这次启动不生效。把模型放回后,请重启服务,再在「记忆检索」**重建一次语义索引** —— 这期间写入的事实
  没有向量,需要重建才能被按意思找到。

### 「资源」里启动 llama.cpp 时,只载入本应用的模型

llama.cpp 会列出这台电脑上别的程序缓存的模型。以前「资源」里点启动时,应用会把它列出的模型全部预先载入,
包括那些与本应用无关的模型,白占显存;本应用自己下载的模型比 llama.cpp 同时能载入的(两个)还多时,还可能把
「判断」或「语义」正在用的那个挤出去。现在点启动只预先载入「判断」和「语义」**正在用**的本机模型;没有用到本机
模型时,只启动 llama.cpp,不载入任何模型。

如果正在用的模型这次没能预先载入,启动后的提示会写明是哪个模型、为什么,以及该怎么做:模型是在 llama.cpp 启动
之后才下载的,而这个 llama.cpp 是本应用启动的,请你重启服务;不是本应用启动的,请你在任务管理器里结束它后再试;
模型在列表里却没能载入时,请看「日志」里的原因。

### 本机 llama.cpp 的重启更稳妥

- **「判断」在用本机对话模型时,不会为了载入新模型自动重启 llama.cpp。** 重启的那几秒里写入的事实会永久没有
  主题标注(实测:重启窗口里写入的 5 条中有 1–2 条没有标注)。这时应用会请你重启服务,新模型会随 llama.cpp
  一起载入 —— **重启后在「记忆检索」里再选一次这个模型**,这次的选择没有保存。
  关掉「判断」时,或「判断」用的是重排模型时,仍会自动重启;但「语义」也在用这个 llama.cpp、「判断」设置了
  本机对话模型、或「语义」设置了本机模型却还没生效(要重启服务才会用上),或者这个 llama.cpp 不是本应用启动的
  时候,同样不会自动重启,而是告诉你该怎么做。
- **llama.cpp 一次回应得慢,不会再让操作报内部错误。** 以前在「资源」或「记忆检索」里的操作可能因此直接失败;
  在重启的那一刻遇到,甚至会让 llama.cpp 停在「没有运行」的状态,没有任何说明。现在重启时会先等旧进程让出
  端口再启动新的;万一旧进程一直不放,会如实告诉你 llama.cpp 现在没有运行,以及怎么处理。
- **llama.cpp 用的端口被一个不像 llama.cpp 那样回应的进程占着时,应用会直接告诉你是哪个端口**,请你在任务管理器
  里结束那个进程,而不是在旁边再启动一个 llama.cpp,最后只报一句「没能启动」。
- **应用自己启动或重启 llama.cpp 的那几秒里,如果端口已经在接受连接、却还没有回应,提示会说「应用正在启动」或
  「应用正在重启」,不会再说成是另一个进程占着端口。** 如果重启停下了旧的
  llama.cpp、新的却没能起来,会如实说明 llama.cpp 现在没有在运行,请你稍等再试,仍然不行就在任务管理器里结束占着
  端口的进程或重启电脑。

### 「智库校验」可以选模型了

两道闸提交前,如果改动涉及智库(`.claude/` 下的文件),应用会先做一次只读复核。它用哪个模型,以前在任何地方都
设置不了,代码里的注释却写着「用便宜一点的模型就够了」—— 实际一直用的是 Claude CLI 的默认模型。现在
「校准 · Cortex」里多了一行「智库校验 · Validate」,可以自己选;留空还是 Claude CLI 的默认模型,和以前一样。
导出/导入「记忆」时,这个设置也会跟着走。

### 判断时只看事实内容

开着「判断」时,判断一条检索结果有没有回答问题,现在只看这条事实的内容,不再同时附上它的主题。用 Claude CLI
判断时,在 240 题的测试集上两种方式的效果测不出差别,而送去判断的文字少了约四分之一。用本机对话模型判断时也是
这样;用 Gemma 3 1B 和 Qwen3 0.6B 测过,两种方式的差别都不显著。

### 本机「判断」模型:实测之后,推荐和说明都改了

这一版在本应用 240 道提问的双语测试集上把几种本机模型都实际测了一遍(不开「语义」;事实都很短时的排第一和带进前八是这
一版重测的),「资源」和「记忆检索」里的推荐与说明按实测结果改写:

- **推荐的本机判断模型是重排模型 BGE Reranker v2 M3**(约 470 MB);llama.cpp 用不了任何显卡、或 BGE 在这台机器上实测太
  慢时推荐在应用进程里运行的「内置」mMiniLMv2,见下文。它只在检索时在本机核对结果;写入事实时的主题标注由 Claude CLI
  完成 —— 每条事实一次调用,消耗账号额度,事实内容会发给 Claude。
- **Gemma 3 1B 不再标「推荐」。** 实测它让答案排第一的次数比不开判断少得多(从 80 题降到 36 题;带进前八没有测出显著差
  别)。它仍然可以选,说明里写着这个结果。**如果你在 1.3.0 里照着「推荐」给「判断」选了它**,建议在「记忆检索」里改选
  :BGE 重排模型(核对留在本机,但主题标注改由 Claude CLI 完成,要消耗账号额度)、Qwen3 0.6B(标注和核对都留在本机,见下面
  一条),或者改回 Claude CLI。
- **新增 mMiniLMv2 重排模型**(约 133 MB,是 BGE 的四分之一多一点):带进前八的次数和 BGE 测不出差别,但也不能算一样好(事
  实都很短时);把答案排第一的次数比 BGE 多(100 对 91,刚过显著的线);速度更快。在约 900–1,200 个字符的长笔记上(这一项是
  在较早的版本上成对量的),两者都分段读时,它把答案带进前八明显少于 BGE(182/240 对 201/240),差距主要在答案写在 1,000个
  字符以后的笔记。它一次最多读512 个词元,较长的事实会分段来读(见下面「长事实分段读」)。模型卡写的许可是Apache-2.0,但
  训练它用的 MS MARCO 数据只许非商业使用。
- **新增 Qwen3 0.6B 对话模型**(下载约 640 MB;运行时 llama.cpp 为它预留的显存约 2.6 GB):标注和判断都在本机完成,不消耗
  账号额度。实测比不开判断好(答案排第一从 80 题增加到 107 题,带进前八从 127 题增加到 152 题),把答案排第一的次数比BGE
  还多,但带进前八的次数远不如 BGE。标注也交给它自己写时(这一项是在较早的版本上量的),和用 Claude 写的标注相比没有测出
  显著差别(但还不能排除排第一最多少约 9 个百分点),仍然明显好过不开判断;它写的主题比较宽泛,常把同一个主题标到不相干的
  事实上,靠「同一个人」把事实串起来的检索可能因此受影响,这一点测试集测不出来。

### 长事实分段读:重排模型分段读长事实

用重排模型做「判断」时,每条候选事实只送得进有限的长度:BGE 和 LAMAR 以前只读前 1,000 个字符。实测发现,答案
落在读不到的后半段时,重排模型不但找不到它,还会把别的事实排到前面,结果比不开判断更难找到。现在较长的事实会
分成几段(相邻两段有重叠,一条最多 5 段)分别打分,取最高的一段;新增的 mMiniLMv2 一段只读约 250–500 个字符,
也按这个办法读。

在 60 条约 900–1,200 个字符的长笔记上实测(240 道提问,答案在开头、中间、末尾、1,000 个字符之后各 60 题;不开
语义、没有主题标注、每次由它挑 8 条上页):答案在 1,000 个字符之后时,BGE 把答案带进前八从 3/60 增加到 51/60;
答案在笔记末尾时,mMiniLMv2 只读开头是 4/60(不开判断是 29/60)、分段读是 44/60;答案在开头时两种读法没有显著
差别;事实都很短时,结果和只读开头完全一样。长事实和短事实混在一起时也量过(30 条短事实与 30 条长笔记,同样的
提问和设置):答案在短事实里的 120 题,分段读没有让它们显著变少(BGE 94 → 91、LAMAR 101 → 99、mMiniLMv2 98 → 97,
这一轮排除不了最多约 4–6 个百分点的损失),答案在长笔记里的 120 题则多带进 30–69 题。代价是长事实的检索更慢:在一块显卡上、模型已加载时,这些长笔记上
BGE 和 LAMAR 每次检索约 3.2 秒(只读开头时约 2.0–2.2 秒),mMiniLMv2 约 1.2 秒;事实都很短时速度不变。

### 较慢的机器:少读几段、来不及就跳过判断,并推荐更小的模型

在只有 CPU 等较慢的机器上,应用按这台机器上测到的速度让长事实少分几段来读(最少只读开头一段 —— 那时写在后面的答案读不
到)。应用每次启动后先按它在这台机器上为这个模型实测的速度估计(没测过、测得比显卡上的参考速度还快、或还有设备没测完而
没定下设备时,按那个参考速度;每个设备都没在限定时间内测完时,按测出的下限;实测见下面「重排模型下载后,先实测它在哪个设
备上最快」);估计偏快时,启动后头一次要读的长事实太多,仍可能等满一分钟、那次检索按没有判断时的顺序返回;单独一次等满(比
如显卡正被别的程序占着、模型在重新载入)只会让应用把速度估计放慢几倍,不会让判断停掉,所以真正慢的机器一般要等满两次,应
用才认定它慢。等满之后,遇到长事实的检索先每条只读开头一段,等有一次在时限内做完、测出速度再按它分段。

预计每条只读开头一段也要超过约 48 秒(刚等满过一分钟时是半分钟)的检索,应用当即跳过判断、按没有判断时的顺序返回,不再每
次等满一分钟;最多每十分钟花几秒重新测一次速度,赶得上就恢复。等满一分钟之后的一两分钟里,检索也会先跳过判断,因为那次打
分还在后台算。跳过的次数写在「记忆检索」的「判断」那一行(「最近 N 次检索里有 M 次因为这台机器太慢,跳过了判断……」),并
建议在「资源」下载「内置」mMiniLMv2 改用它(在应用进程里运行,不需要 llama.cpp)—— 即使已经装了别的重排模型,「资源」也
会推荐它。

llama.cpp 用不了任何显卡时,应用直接推荐「内置」mMiniLMv2 而不是 BGE(见下面「「判断」的「内置」重排模型」)。llama.cpp
上的 mMiniLMv2 也在一台只用 CPU 的笔记本上实测过(Intel Core Ultra 9 185H,不用显卡,llama.cpp b10549;60 条约 900–1,200
个字符的长笔记、240 道提问、不开语义、没有主题标注、每次由它挑 8 条上页):mMiniLMv2 分段读每次检索约 17.5 秒、每次都
在一分钟内判断完,答案带进前八 180/240(不开判断 104/240);同一台机器上BGE 几乎每次都来不及判断,结果和不开判断一样
(104/240)。LAMAR 没有在只用 CPU 的机器上量过。集成显卡也算显卡,所以只有集成显卡的笔记本不会因为这一条被推荐「内置」
mMiniLMv2 —— 那种机器见下一条。

### 重排模型下载后,先实测它在哪个设备上最快

下载重排模型后,应用下一次自己启动 llama.cpp 时,会先在 CPU 和每块显卡上各测一次它的打分速度(一个一个测,每个几秒到一分
多钟;启动画面会说正在测哪一个,「资源」里的「启动」按钮和「记忆检索」里选模型时会说测了多久),之后让它在最快的那个设备
上运行。已经下载了重排模型的,更新到这一版后应用第一次自己启动 llama.cpp 时也会测。测到的速度、选的设备和日期写在「资
源」里它那一行。某个设备没测出结果(比如当时显卡正被别的程序占着)时,之后应用每次自己启动 llama.cpp 时会再测它,一共最
多三次;还有速度不明的设备(比如上次没能载入模型)等着重测时,应用先不替它选设备,仍由 llama.cpp 自己选 —— 上次在限定时间
内没测完的设备已经比测出结果的慢,不用等它;模型文件、llama.cpp 版本、设备列表或应用的测法变了会重新测,更新显卡驱动不
算。只有重排模型这样选设备,嵌入模型和对话模型仍由 llama.cpp 自己选;正在运行的 llama.cpp 不是本应用启动的时候,应用不
替它测。

为什么:在一台笔记本上(Intel Core Ultra 9 185H 自带的 Arc 集成显卡,llama.cpp b10549),两个重排模型在集成显卡上都比同一
台机器的 CPU 慢(mMiniLMv2 约 6–7 倍,BGE 约 3 倍)。llama.cpp 列出的设备里看不出哪块是集成显卡,机器上只有集成显卡时它
自己就会用上那块。只让它看到这块集成显卡时,应用为两个模型都选了 CPU;BGE 连在 CPU 上,按测到的速度推算,一次默认检索(最
多给判断看 96 条,每条都是约 1,000 字的长事实)也约要 130 秒,超过应用送出一次判断的约 48 秒上限,所以「资源」测完就改为
推荐「内置」mMiniLMv2(还有速度不明的设备等着重测时先不改)。同一台笔记本能用它的独立显卡(RTX 4080 Laptop)时,两个模型
都选了独立显卡,和 llama.cpp 自己选的一样,所以在那台机器上,重排模型运行的设备没有变。这些都只是一台机器上的数。BGE 要
下载之后才测得出,所以只有集成显卡的机器上,「资源」一开始仍会推荐 BGE,测出太慢后才改为推荐「内置」mMiniLMv2。

### 判断卡住时,检索结果照常

本机对话模型偶尔会一直生成下去不停。以前「判断」这样卡住时,整次检索会在两分钟后退回成只按文字匹配的结果。现在判断最
多等一分钟:等不到就当这次没有判断,检索照常给出原来的排序。应用调用本机对话模型时会要求它**关掉「思考」**,启动它时也
会**限制它一次最多生成的长度**,所以像 Qwen 这样会「先想一想」的模型不会每次都想半天。

### 修改过的事实,没来得及重新索引也会补上

修改一条已有的事实时,如果这次没能重新建立它的检索索引(比如判断在标注时卡住了),以前它会一直留在旧内容的
索引上 —— 新内容只能按字面匹配找到,要等手动重建索引才会参与关联和排序;从「记忆」导入时修改了内容的事实也是
这样。现在这种事实会在下次启动时自动重新索引;从「记忆」导入的事实(修改过的和新的)在导入后就会在后台建立
索引,不用等重启。

### 本机对话模型占的显存更少

应用启动本机对话模型时,现在给它的上下文设了上限(16,384 个词元)。以前 llama.cpp 会按模型训练时最长的上下文
预留显存 —— 像 Qwen3 0.6B 这样的模型会占去约 5.4 GB;现在约 2.6 GB。判断的提问在这个上限里放得下;极少数
一次要核对几百条很长事实的检索放不下时,这次判断会跳过,检索照常。

### 本机嵌入模型能读更长的事实

「语义」用 llama.cpp 上的 EmbeddingGemma 时,以前一条事实只读得进约 750 个汉字(英文约 2,500 个字符),更长的事实建立不
了向量。现在它一次读满自己的上限 2,048 个词元(实测约 3,000 个汉字、约 10,000 个英文字符);显存多用约 46–83 MB,短查询
的速度不变(一块独立显卡上每次约 31 毫秒)。更早写入、当时太长而没有向量的事实,更新后第一次启动时会补上:应用会为已有的
事实原地重新计算一次向量(这次启动因此会慢一些),已学到的排序和关联都保留。超过上限的事实仍能按关键词和图谱找到,只是没
有向量,应用也不会一直重试它们。

### 重建语义索引不再丢掉已学到的排序和关联

以前在「记忆检索」里重建语义索引,会丢掉图谱已经学到的排序和关联,每条事实还要重新做一次主题标注(开着「判断」时消耗账
号额度)。现在用嵌入模型时是原地重新计算向量:每条事实一次嵌入,不调用模型标注,排序、关联和主题都保留。实测一百条短事实
:llama.cpp 上一块独立显卡约 3 秒、只用 CPU 约 6 秒,内置嵌入模型约 5 秒。之前没有索引的事实会顺带补建,开着「判断」时
这些事实每条多一次模型调用。

- **更换嵌入模型后不用再手动重建**:重启服务时会自动为已有的事实重新计算向量(重启因此会多花一些时间,每条事实约 30–60
  毫秒,这期间应用显示正在启动)。重启之前点「重建索引」会被拒绝并说明原因 —— 以前会用旧模型算一遍、显示成功,重启后「
  语义」却什么也找不到。
- **嵌入模型没有响应时,重建会直接拒绝**,不会先丢掉已有的索引。
- **用 Claude CLI 补写说法时**,完成后会分别说补写成功和没成功的条数;以前 Claude CLI 没有登录时也会显示全部补写完成。

### 嵌入模型中途停下时写入的事实,会在下次启动补上

嵌入模型没有响应时写入的事实,先只能按关键词找到,下次启动时会补上向量(开着「判断」的话,补的时候还要再做一次主题标注);
以前这些事实会一直没有向量,除非手动重建索引。恢复备份时的索引重建如果没有全部完成,已经建立的会保留,其余的下次启动补
上。

### 模型设置的保存方式改了(升级时自动迁移)

「校准 · Cortex」里自动评分的模型和「判断」的模型,现在按「后端 + 模型」一起保存,升级后第一次启动会自动迁移原来的设置。
模型名里不能再有逗号。「判断」因为本机模型不见了而退回 Claude CLI 时,遗留的旧设置会在启动时清掉。**注意**:把这一版导
出的「记忆」文件导入到 1.3 或更早的版本时,自动评分的模型设置不会带过去。

### 其他

- 定时任务会等启动完成后才开始运行。
- 写入事实时如果主题标注没有得到回应(比如 Claude CLI 没有登录),「日志」里会写明哪条事实没有主题标注。
- 「判断」用本机对话模型时,改由每次调用时要求它不要「思考」,不再靠启动参数;在三个本机对话模型上实测过,效果和以前一样。
- 判断读事实内容时的截断改由应用所用的记忆库来做:400 个字符以内完全一样;更长的事实截断的位置可能早一些,最多早到一半(
  按测试集里 90 条长笔记算过:20 条少读 1–12 个字符)。
- 只有自动评分会用到读取文件的工具;记忆的标注、核对和补写说法不再带上这些工具。
- 重排模型的分段读法和记忆库新版自带的分段方法实测对比过,保留应用自己的读法:BGE 在长笔记上用记忆库的方法明显更差(带
  进前八 171 对 201),LAMAR 没有差别,mMiniLMv2 用记忆库的方法更好(带进前八 196 对 182);应用自己的读法还能按这台机器的
  速度决定读几段,记忆库的方法做不到。
- 也试过让应用自己分段时在句子边界下刀,实测没有达到采用的标准(mMiniLMv2 在长笔记上带进前八 182 对 188,差别不显著),所
  以分段方式不变。

### 「判断」的「内置」重排模型:不需要 llama.cpp

「判断」现在可以选在应用进程里运行的「内置」重排模型 mMiniLMv2:用 CPU 运行,不需要 llama.cpp,没有常驻服务,也没有端口,
在「资源」里下载(约 136 MB)。它只做检索时的核对,写入事实时的主题标注仍由 Claude CLI 完成(每条事实一次调用,消耗账号额
度)。在一台笔记本的 CPU 上实测(Intel Core Ultra 9 185H;240 道提问的双语测试集和 60 条长笔记,不开语义,每次由它挑 8 条
上页):它判断得和 llama.cpp 上的同一个 mMiniLMv2 一样好,每次检索却快得多(短事实约 0.47 秒对 0.82 秒,长笔记约 8.1 秒对
20 秒)。所以 llama.cpp 用不了任何显卡、检索因为机器太慢跳过了判断、或 BGE 在这台机器上实测太慢时,「资源」和「判断」
那一行现在推荐的是它 —— 这样的机器上「判断」不需要再装 llama.cpp。有独立显卡时推荐的仍是 llama.cpp 上的 BGE,它在显卡
上更快(短事实约 0.30 秒,长笔记约 1.2 秒)。「内置」打分时应用会多占约 0.7–1.0 GB 内存,第一次判断时先载入约 1.3 秒。

### 规划助手的边界更牢了

- **Windows 上不再有应用管不到的 PowerShell。** Claude CLI 在 Windows 上默认会给规划助手一个 PowerShell 工具,应用的
  边界检查看不到它:「执行」阶段它可以改动或删除应用自己的设置、数据库和证书、site.json 和上传的文件。现在应用启动规
  划助手时去掉了 PowerShell 和后台监视工具。
- **命令行里也关上了几条路。** 助手在 Bash 里不能再启动别的命令行或解释器(PowerShell、cmd 等),也不能改写或读取应用自
  己的文件(state 文件夹、site.json、.git、.claude 里的设置和 .mcp.json)。守护脚本本身移到了助手碰不到的位置,文件名结
  尾多一个点或空格、大小写不同等写法也不再能绕过保护。
- **计划阶段不再有命令行**,也只能读数据文件夹里的内容;命令行只在你批准计划后的「执行」阶段才有。
- 这些检查是尽力而为:助手自己写的脚本里运行的代码,或用变量拼出来的路径,仍可能绕过 —— 要完全关上需要操作系统级的沙箱。
  助手用到的每个工具和访问的网址仍都记在对话记录里。

### 规划助手的文件工具

规划助手有了移动/重命名、删除文件,以及查看文件大小和修改时间的工具。它们只能用在计划、家庭资料、知识库和页面的可写范
围内,也只在「执行」阶段可用;改动和其他编辑一样出现在改动审阅里,由你确认后才提交。

### 命令行(Git Bash)

没有装 Git for Windows 的机器上,规划助手默认没有命令行(以前用的是一个应用管不到的 PowerShell),但仍可用上面的文件工具
和读取、搜索。「资源」里可以下载一个 Git Bash(约 59 MB 下载、约 385 MB 安装),下载后助手就有一个应用能把关的命令行,不
需要重启。已经装了 Git for Windows 的机器不用下载;你自己设置过 Git Bash 位置的,应用不改这个设置。

### 应用启动的其他程序看不到它的设置和密钥

- 规划助手写的工具(脚本能力)运行时只拿到 Node 需要的几个环境变量,看不到应用的访问令牌等设置;以前继承下来的
  `NODE_OPTIONS` 甚至可以让这样的工具连上网络,现在关上了。
- 应用启动的 Claude CLI 只用你登录的订阅账号:应用启动时环境里的 API 密钥、其他服务商的开关、别的服务地址都会被忽略,
  启动日志里会写明忽略了哪些(只写名字,不写值)。
- 应用自己的访问令牌和证书密码不再传给它启动的任何程序。
- 应用的 git 命令不再受启动它的环境里的 git 设置影响(比如从另一个仓库里启动时,不会误把那个仓库当成数据仓库)。
